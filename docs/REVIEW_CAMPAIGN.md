## Why these twelve classes

evaluation collections with few new reviews submitted directly to EagleEvals.

enrollment, page traffic, or distinct students. These are historical catalog
entries, not a claim that every course is offered this semester.

## Seven-day launch

1. **Before posting:** Giulia checks the copy and picks appropriate groups or
   people. Verify the public page and at least one prefilled link on mobile.
   The form must keep professor and semester available, preserve drafts after
   errors, and accept honest feedback with optional detailed fields.
2. **Record Day 0:** save the actual launch time in UTC and run the aggregate
   baseline query below. The research baseline is two native reviews across two
   of the twelve courses; it may have changed before launch.
3. **Days 1–2:** start with a small number of groups Giulia already participates
   in and a few personal asks. Use a course-specific link when the audience
   knows that course. Keep a simple count of approved posts and the date, not a
   list of who reviewed or which review belongs to which person.
4. **Days 3–4:** manually check aggregate new reviews and course coverage. If a
   student reports trouble, fix that friction. Avoid repeating the same post in
   the same group; use another relevant audience only if posting is welcome.
5. **Day 7:** run the same aggregate query for exactly seven days. Review the
   totals and decide whether the process is worth repeating. This checklist does
   not create scheduled reminders or automated messages.

An initial **goal, not a forecast**, is 30 newly published native reviews across
at least eight of the twelve courses, including at least six of the ten courses
that currently have zero native submissions. Report new published reviews,
course coverage, and the semester mix separately from imported totals. With
anonymous reviews and no tracking links, this is growth during the campaign
window; it cannot prove which post or person caused each submission.

## Aggregate measurement

Use an authorized read-only connection. Bind `$1` to the actual UTC launch time.
Run before posting to save the native baseline, then again after seven days.
This reads only aggregate counts and public course codes; no review text or
reviewer identifiers are needed. An unpublished or removed review is excluded.

```sql
WITH selected AS (
  SELECT id, code FROM courses WHERE code IN (
    'ACCT1021','MFIN1021','MKTG1021','CSCI1101','MATH1100','BIOL2040',
    'CHEM1110','ECON2228','ENGL1010','PHIL1071','HIST1001','NURS2231'
  )
), bounds AS (
  SELECT $1::timestamptz AS starts, $1::timestamptz + interval '7 days' AS ends
)
SELECT s.code,
  count(sc.id) FILTER (WHERE sc.created_at < b.starts)::integer AS native_before_launch,
  count(sc.id) FILTER (
    WHERE sc.created_at >= b.starts AND sc.created_at < b.ends
  )::integer AS new_native_in_seven_days
FROM selected s CROSS JOIN bounds b
LEFT JOIN student_comments sc ON sc.course_id=s.id
  AND sc.published AND sc.source='eagleevals_anonymous'
GROUP BY s.code ORDER BY s.code;
```

Sum `new_native_in_seven_days` for the review total. Count rows with a positive
new count for the number of courses reached. Count rows whose baseline is zero
and new count is positive for newly covered courses. Record the Day 0 baseline
when launching, so later moderation does not silently rewrite the starting
numbers. A review posted during the week may describe an older class; use its
explicit semester when reporting how recent the experience was.
